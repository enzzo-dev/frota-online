Drivers set the price.
This API moves the freight.

Sign people in today. Freight requests, proposals and deliveries are built on the same foundation and arrive next.

Base URL /api/v1

Available now: accounts, driver onboarding with file uploads, freight requests, proposals, delivery tracking, notifications, subscriptions and Pix payments through Asaas. Next: sending the driver's position and filtering freights by region.

Make your first call in four stops

Each stop runs a real request against this server and keeps the result for the next one. Nothing here is mocked.

How sessions work

      

        
15 min
Access token lifetime. It is a signed JWT carrying your id, e-mail and role.

        
30 days
Refresh token lifetime. It is random, shown once, and stored on our side only as a hash.

        
1 use
Every refresh token works once. Using it again is treated as theft and ends the session.

      

      
Roles are Customer, Driver and Admin. Sign-up only creates the first two. Passwords need 8 to 128 characters with an upper case letter, a lower case letter and a digit.

    Driver onboarding
    
      
    A driver cannot send proposals until an admin approves the profile. These are the calls, in order. Authenticate as a Driver for steps 1 to 6 and as an Admin for step 7.
    
      
    
        
    
          
    StepCallWhat happens
    
          
            
    1GET /terms/pending then POST /terms/acceptAccept every active term. Each acceptance stores the time and IP address.
    
            
    2PUT /driver/profileSend taxId (CPF or CNPJ, letters allowed), CNH and category. The tax id is required and checked by its digits before anything is saved. Repeat the call to correct data while the profile is a draft or rejected.
    
            
    3POST /driver/vehiclesRegister at least one vehicle. Plates accept ABC1234 and ABC1D23.
    
            
    4POST /driver/documentsRegister the files you already uploaded (see File uploads: ask for a pre-signed URL first). The storage key must start with drivers/{your user id}/.
    
            
    5GET /driver/profileThe checklist shows what is still missing: terms, vehicle, document.
    
            
    6POST /driver/submitMoves the status to PendingReview and locks the profile. An incomplete checklist returns the missing items.
    
            
    7GET /admin/drivers, then approve or rejectThe admin reviews the file. Approval or rejection (with a reason) sends an e-mail. A rejected driver edits and submits again.
    
              
        
    
      
    
      
    In Development the API creates an admin on first start (admin@frotaonline.local, password from Seed:Admin:Password in appsettings.Development.json) and publishes version 1.0 of the terms. Sign in with it to try step 7.
    
    
    

    
    
      
    Marketplace
    
      
    The customer posts a freight, approved drivers bid with their own price, and the customer picks one. The platform never touches the freight money.
    
      
    
        
    
          
    StepWhoCallWhat happens
    
          
            
    1CustomerPOST /addressesRegister every pickup and delivery address. State must be a valid UF and the ZIP has 8 digits. Optional latitude and longitude, always sent together (only one of them is a 400): the app looks up the typed address in a public geocoding API and sends the point. The API does not geocode, and without the point the address works but its route cannot be drawn on the map. Customers can be people or companies.
    
            
    1bCustomerPOST /freights/route-previewWith the addresses chosen, in the order of the run, shows the route before you request the freight: pins, driving distance (meters), duration (seconds) and the line to draw. Addresses need latitude and longitude (take them from the map picker when saving the address), otherwise route.missing_coordinates lists which ones lack a pin. If the routing engine is down, distance and duration are null and the path is empty: draw the pins and a straight line. GET /freights/{id}/route gives the same for a created freight.
    
            
    1cCustomerPUT /addresses/{id}, DELETE /addresses/{id}Edit replaces every field, so send latitude and longitude again (together) or they are cleared. Only an address no freight ever used can be edited; otherwise address.in_use and the app saves a new one. Delete removes an unused address for good; one used only by finished freights leaves the list but is kept for their history; one in an open freight or a delivery in progress is refused with address.in_active_use: cancel that freight first.
    
            
    2CustomerPOST /freightsSend stops in the order the driver follows, each one a Pickup or a Delivery with optional items and a note. A freight can have several pickups and several deliveries; the first stop must be a pickup and the last a delivery, the final address. Needs every active term accepted. Without scheduledPickupAt the freight is for today and takes proposals for 5 minutes; a scheduled one takes them for 24 hours (UTC, trailing Z).
    
            
    3DriverGET /driver/freights/openOnly freights whose vehicle type matches one of your active vehicles. Each freight shows how many pickups and deliveries it has and, per stop, the area and the items. Street addresses stay hidden until approval.
    
            
    3bDriverGET /driver/freights/open, mapEach freight carries routeDistanceMeters and routeDurationSeconds so you can judge the run, and each stop has approxLatitude/approxLongitude rounded to about 1 km: pin the area on the map, never the street. After winning, GET /driver/deliveries/{id}/map returns the exact pins and the route line.
    
            
    4DriverPOST /driver/freights/{id}/proposalsPick a vehicle of the right type that carries the weight, and set the price. One pending proposal per freight; withdraw it to change your mind.
    
            
    5CustomerGET /freights/{id}/proposalsPending proposals ranked by price, cheapest first. Ties go to the earliest.
    
            
    6CustomerPOST /freights/{id}/proposals/{proposalId}/approveCreates the delivery, books the driver's agenda (2 hours plus 1 hour per stop, from the first pickup), rejects the other proposals and closes the freight. A driver already booked in that period returns proposal.driver_busy.
    
            
    7DriverGET /driver/deliveries, then GET /driver/deliveries/{id}/routeLists the deliveries you won and opens the route with full addresses. view=Full shows every pickup and delivery at once, as an overview of the run. view=Next shows only the stop to do now, so the app can go one stop after the other. Each stop lists its items.
    
            
    8DriverPOST /driver/deliveries/{id}/startLeaves for the first pickup. Scheduled becomes ToPickup.
    
            
    9DriverPOST /driver/deliveries/{id}/stops/{stopId}/completeCompletes the next stop; stops must be done in order (delivery.stop_out_of_order). The first pickup moves the delivery to PickedUp and InTransit, and the last stop marks it Delivered, accrues the R$ 4.90 fee and frees the agenda. Optional note, coordinates and a DeliveryProof file (register it first with POST /driver/documents).
    
            
    10DriverPOST /driver/deliveries/{id}/incident or /cancelReports an incident (then only cancelling is possible) or cancels. The driver can cancel before the first pickup (Scheduled, or already on the way in ToPickup) and after an incident. Once the first pickup is completed (PickedUp or InTransit) it is refused with delivery.invalid_status: report an incident first. The agenda is freed and no fee accrues.
    
            
    11CustomerGET /deliveries, GET /deliveries/{id}Follows the run: status, driver and vehicle, stops with completion times, payment status and the event timeline. POST /deliveries/{id}/cancel works only before the cargo is picked up.
    
            
    12DriverPOST /driver/deliveries/{id}/paymentAfter Delivered, confirms the customer paid (Pix, Cash, Card or Other). Once per delivery. The money never passes through the platform.
    
            
    13Driver / AdminGET /driver/fees, GET and POST /admin/drivers/{id}/fees[/settle]The fee ledger: R$ 4.90 accrues per delivered freight and the admin records what the driver paid. A settlement cannot exceed the open balance (fee.exceeds_balance).
    
              
        
    
      
    
      
    A job expires freights and proposals past their window: every 30 seconds in-process in development, and in production Cloud Scheduler calls POST /internal/jobs/expire (and /internal/jobs/dispatch-notifications for pushes) every minute, authenticated with a Google OIDC token (Jobs:Audience, Jobs:ServiceAccountEmail). Until it runs, the API already refuses proposals that arrive late.
    
    
    

    
    
      
    Notifications
    
      
    Every business event leaves a notification for the right person, in the same transaction as the operation that caused it. It is the in-app inbox, and a background worker also sends it as a push to the devices the person registered.
    
      
    
        
    
          
    CallWhat happens
    
          
            
    PUT /devicesRegister the phone: { "token": "...", "platform": "Android" | "Ios" | "Web" }, the token the push provider gave the app. Call it after every login and when the provider issues a new token. Repeating it is harmless; if the same phone signs in as someone else, the token moves to that account.
    
            
    DELETE /devices?token=...Call it on logout so the next person using the phone does not receive this account's notifications. Always 204.
    
            
    GET /notificationsThe inbox, newest first. Query: unreadOnly, page (from 1), pageSize (1 to 100, default 20). The response has items, unreadCount for the bell badge and hasMore for infinite scroll. Each item has type, title, body (Portuguese), and targetType + targetId, which say what to open when it is tapped: Freight, Proposal, Delivery, DriverProfile or Fee.
    
            
    GET /notifications/unread-countJust { "unread": 3 }, cheap enough to poll for the badge.
    
            
    POST /notifications/{id}/read, POST /notifications/read-allMark one or all as read. Idempotent. Someone else's notification is a 404 notification.not_found.
    
          
    GET /notifications/preferences, PUT /notifications/preferencesTwo switches, both on by default: newFreightAlerts (drivers are told when a freight that fits opens) and pushEnabled (off keeps the inbox but silences the phone). Send only what changes, e.g. { "newFreightAlerts": false } turns the new-freight alerts off and keeps every other push.

    Compatible freight alert. When a freight is posted, every driver it fits is told: approved, with an active vehicle of the required type and enough capacity, free in the agenda during the run, and with the alert on. The customer who posted it is never told, and at most 500 drivers are alerted per freight. There is no distance filter yet (the app does not collect where the driver works), so the alert goes to compatible drivers in any city.
    
      
    One driver action in the middle of a run sends one notification (the most relevant one), even when the delivery moves through more than one status. The push carries the same data as the inbox item (notificationId, type, targetType, targetId). A failed send is retried a minute later, up to 5 times, and the inbox entry is there either way; someone who already opened the notification in the app gets no push. Set Push:Provider to Firebase to send real pushes through Firebase Cloud Messaging (credentials from Application Default Credentials, so on GCP the runtime service account); the default only writes them to the log. Deleting an account (LGPD) erases its notifications and device tokens.
    
    
    

    
    
      
    File uploads
    
      
    Files never pass through the API. The app sends them straight to the storage with a pre-signed URL and the API checks the result.
    

    
        
    
          
    StepCallWhat happens
    
          
            
    1POST /driver/documents/upload-urlSend { "kind": "DriverDocument" | "VehiclePhoto", "contentType": "image/jpeg" | "image/png" | "application/pdf" }. The answer has storageKey, uploadUrl, method (PUT), headers, maxBytes (10 MB) and expiresAt (15 minutes).
    
            
    2PUT {uploadUrl} (to the storage, not to this API)Send the file body with exactly the headers you received. A different type or a bigger file is refused by the storage.
    
            
    3POST /driver/documentsRegister the storageKey. The API looks at the real object: missing is 409 driver.file_not_uploaded; over 10 MB or not JPEG, PNG or PDF deletes the object and answers 400 (driver.file_too_large / driver.file_type_not_allowed). The size and type saved are the storage's, not the ones the app declared.
    
            
    AdminGET /admin/drivers/{driverId}/files/{fileId}/urlA read link that expires in 10 minutes. The bucket is never public.
    
                
        
    
      
    
      
    Without Storage__Provider=Gcs the upload-url endpoint answers 409 storage.not_configured and POST /driver/documents keeps trusting what the app sends (development only). Deleting an account also deletes the person's objects from the storage.
    
    
    

    
    
      
    Payments (Asaas and Mercado Pago)
    
      
    Subscriptions, a Pix issued by the app with split, and automatic collection of the platform fee. Only paying a freight by card makes the card pass through this API (and it is never stored). Every endpoint here answers 409 payments.not_configured until the server has Payments__Provider=Asaas (and Payments__WalletProvider=MercadoPago for Apple Pay), and 503 payments.unavailable when Asaas cannot be reached.
    

      
    Driver subscription
    

    
        
    
          
    CallWhat happens
    
          
            
    GET /driver/subscriptionThe two plans (Basic R$ 79.90 up to 3 vehicles, Full R$ 99.90 with no limit) and the current subscription. hasAccess is true while the driver is inside a period they paid for.
    
            
    POST /driver/subscription{ "plan": "Basic" | "Full" }, approved drivers only. Returns paymentUrl: open it so the driver pays by Pix, boleto or card. The plan turns Active when Asaas confirms the payment; each paid month adds one month. Asking again for the same plan before paying returns the same link.
    
            
    DELETE /driver/subscriptionStops future charges. The driver keeps the access already paid for until endsAt.
    
                
        
    
      
    
      
    Basic allows 3 active vehicles: adding a 4th answers 409 subscription.vehicle_limit, and choosing Basic with more than 3 answers subscription.too_many_vehicles. When the server has Subscriptions__RequiredToPropose=true, a driver without a paid period may take one freight; after that, sending a proposal answers 403 subscription.required. The rule applies when the proposal is sent and again when the customer approves it, so only the first approved proposal gets the free freight (the customer sees 409 proposal.driver_unavailable on the others and picks another). A cancelled delivery gives the free freight back. Off by default.
    

      
    Paying a freight by Pix, split between driver and platform
    

    
        
    
          
    CallWhat happens
    
          
            
    PUT /driver/payout-accountThe driver links their own Asaas account: { "walletId": "<uuid>" }. It is where their share is sent. GET shows whether it is set.
    
            
    POST /deliveries/{id}/pixCustomer, after the delivery is completed. Send { "taxId": "<payer CPF or CNPJ>" } (Asaas requires it; the app does not store it). Returns pixPayload (copia e cola), pixQrCode (base64 PNG), expiresAt, driverReceives and platformFee. The driver gets price minus R$ 4.90 straight in their account; the platform never holds the driver’s money. Asking again returns the same Pix while it is valid.
    
                
        
    
      
    
      
    When Asaas confirms the payment, it becomes Paid, the R$ 4.90 fee in the driver’s statement is settled by itself, and both sides are notified. Without a linked account the answer is 409 payments.driver_without_payout_account: pay the driver directly and let them confirm with POST /driver/deliveries/{id}/payment.
    

      
    Paying a freight by credit card
    

    
        
    
          
    CallWhat happens
    
          
            
    POST /deliveries/{id}/cardCustomer, after the delivery is completed. New card: { "card": { "holderName", "number", "expiryMonth", "expiryYear", "ccv" }, "holder": { "taxId", "postalCode", "addressNumber", "phone" }, "saveCard": false }. Saved card: { "savedCardId": "<uuid>" }. This is the only route where the card passes through the API: it goes on to Asaas in the same request and is never stored or logged. HTTPS only. The split is the same as the Pix. The payment stays Pending until Asaas confirms; a refused card answers 409 payments.card_declined and nothing is charged.
    
            
    GET /customer/cardsSaved cards: id, brand and last4. Only Asaas’s token is kept, never the number. At most 5.
    
            
    DELETE /customer/cards/{id}Removes a saved card.
    
                
        
    
      
    
      
    While a card or wallet payment is being confirmed, another attempt answers 409 payments.in_progress. If Asaas refuses the capture afterwards, the payment becomes Failed, the customer receives PaymentFailed and can try again.
    

      
    Apple Pay through Mercado Pago
    
      
    Before promising it to customers: Mercado Pago documents Apple Pay (iOS only, Visa and Mastercard, after commercial enablement) and does not document Google Pay; Asaas documents neither wallet. Confirm with Mercado Pago Brazil. The backend takes a card token made by the Mercado Pago SDK in the app, whichever wallet it came from.
    

    
        
    
          
    CallWhat happens
    
          
            
    POST /driver/wallet-account/authorizationThe driver connects their own Mercado Pago account once. Returns authorizationUrl (valid 15 minutes): open it in the browser. After they allow it, Mercado Pago calls GET /callbacks/mercadopago/oauth, which stores the tokens encrypted.
    
            
    GET /driver/wallet-account{ "connected": true | false }.
    
            
    DELETE /driver/wallet-accountDeletes the stored tokens.
    
            
    POST /deliveries/{id}/walletCustomer. After Apple Pay returns the token through the SDK: { "cardToken": "...", "paymentMethodId": "visa" }. The payment is created on the driver’s account with the R$ 4.90 commission for the platform. approved settles at once; in_process waits for Mercado Pago’s notice. A driver without a connected account: 409 payments.driver_without_wallet_account.
    
                
        
    
      
    
      
    Mercado Pago deducts its own fee first and the platform commission comes out of what is left, so the card fee falls on the driver’s side. The server needs Payments__WalletProvider=MercadoPago and the keys described in the README.
    

      
    Paying the platform fee
    

    
        
    
          
    CallWhat happens
    
          
            
    POST /driver/fees/pixA Pix for the whole open balance (freights paid outside the app). When it is paid the statement is settled automatically and the driver receives FeeSettled. The minimum charge is R$ 5.00: below it the answer is 409 fee.below_minimum and the balance waits.
    
                
        
    
      
    
      
    Webhook (server to server)
    
      
    POST /webhooks/asaas is called by Asaas, never by the app, and is protected by the asaas-access-token header. Each event id is processed once, so a repeated delivery changes nothing. Handled: PAYMENT_RECEIVED and PAYMENT_CONFIRMED (subscription, freight Pix, fee Pix) and SUBSCRIPTION_DELETED / SUBSCRIPTION_INACTIVATED. Anything else is acknowledged and ignored.
    
      
    POST /webhooks/mercadopago is called by Mercado Pago and protected by the x-signature signature. The notice only says something changed: the real status is read from Mercado Pago, and approved settles while rejected/cancelled mark the payment Failed. At Asaas, a card refused at capture arrives as PAYMENT_CREDIT_CARD_CAPTURE_REFUSED.
    
    
    

    
    
      
    Privacy and data deletion (LGPD)
    
      
    Every signed-in user can see what the platform holds about them and ask for it to be erased, as the LGPD (art. 18) requires.
    
      
    
        
    
          
    CallWhat happens
    
          
            
    GET /me/dataExports everything held about the user as JSON: account, tax id and CNH, vehicles, addresses, files, accepted terms, freights, proposals and deliveries.
    
            
    POST /me/deletionSend { "password": "...", "confirm": true }. The account is anonymized: name, e-mail, phone, documents, plates and street addresses are erased, files and sessions are deleted, open freights are cancelled and pending proposals closed. The response lists what stays.
    
              
        
    
      
    
      
    Freights, proposals, deliveries and payment records stay without identifying anyone, because the law requires them for audit and tax (LGPD art. 16). Deletion is refused while a delivery is in progress (privacy.active_deliveries) and for administrators. Access tokens already issued last up to 15 minutes, so discard them in the app after deleting. The e-mail becomes free for a new sign-up.

    Errors
    
      
    Every failure comes back as JSON in the problem details format. Read the status code first, then title for a stable code you can branch on.

{
  "title": "auth.email_in_use",
  "detail": "Este e-mail já está cadastrado.",
  "status": 409
}
    
        
    
        
    
          
    A request with invalid fields
    
          
    HTTP/1.1 400 Bad Request
{
  "title": "Um ou mais erros de validação ocorreram.",
  "status": 400,
  "errors": {
    "Password": ["Password must contain a digit."]
  }
}

    409delivery.invalid_statusThe delivery is not in a status that allows this action.
